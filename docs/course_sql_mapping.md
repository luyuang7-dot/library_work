# 课程知识点与本项目 SQL 实现对应文稿

## 1. 先回答一个核心问题：这个项目到底有没有用 SQL

有，而且用得比较系统，只是不是以“手写很多 `.sql` 文件”的形式出现，而是主要通过以下三种方式落地：

1. ORM 生成 SQL  
   项目主体使用 `Flask-SQLAlchemy / SQLAlchemy`。也就是说，很多增删改查并不是手写 `SELECT/INSERT/UPDATE/DELETE`，而是通过模型、关系、查询链式调用，让 ORM 在运行时生成 SQL。

2. 迁移工具生成和执行 DDL  
   项目使用 `Alembic` 做数据库迁移，负责把模型结构同步到数据库，属于课程里“数据库和表管理”的实际工程化版本。

3. 少量原生 SQL  
   项目中确实存在少量手写 SQL，例如：
   - 健康检查中的 `SELECT 1`
   - 兼容旧库时的 `ALTER TABLE ... ADD COLUMN ...`
   - 旧用户数据修复时的 `UPDATE users SET ...`

从代码结构上看，这个项目没有单独的 `.sql` 脚本文件，但它确实大量依赖 SQL，只是大多数 SQL 是由 ORM 和迁移层间接生成的。

## 2. 项目的数据库技术路线

- 生产默认数据库是 MySQL，见 `config.py` 中的 `mysql+pymysql://root:@localhost:3306/library_work?charset=utf8mb4`
- 测试环境使用内存 SQLite，说明项目在设计上同时考虑了“真实运行环境”和“轻量测试环境”
- 模型定义集中在 `app/models.py`
- 迁移入口在 `app/__init__.py` 的 `init-db` 命令和 `migrations/versions/20260624_0001_course_project_baseline.py`
- 启动时还带有一次“旧库修复”逻辑，位于 `app/services/schema_bootstrap.py`

因此，如果从课程角度概括，这个项目不是“只会写几条查询语句”的级别，而是已经形成了“关系模式设计 + 约束 + CRUD + 查询优化意识 + 事务控制 + 迁移维护”的完整数据库工程链路。

## 第1章 数据库系统概论

### 1. 数据、信息与数据管理

课程强调“数据是记录，信息是数据所表达的含义”。本项目中，这一点的体现非常明显：

- `Document` 表负责存储“文献记录”本身，例如标题、摘要、年份、DOI、阅读状态
- `Author`、`Keyword`、`Tag`、`Source`、`Publisher` 等表把不同类型的信息拆分成独立实体
- 通过外键和关联表把这些实体重新组织成有意义的信息网络

换言之，项目不是把一篇文献的所有内容塞进一张大表，而是把“原始数据”组织成“可管理、可查询、可复用的信息结构”，这正是数据库管理思想的直接体现。

### 2. 数据库、数据库系统、DBMS

课程里的数据库系统包含数据、DBMS、应用程序和用户。本项目的对应关系是：

- 数据库：MySQL/SQLite 中的实际表与记录
- DBMS：MySQL 或 SQLite
- 应用程序：Flask Web 系统
- 用户：普通用户、待审核用户、管理员、次级管理员

也就是说，本项目本身就是一个典型的“数据库系统”实例，而不仅仅是一个“有数据库的程序”。

### 3. 数据模型与三级抽象思想

课程提到“现实世界 -> 信息世界 -> 计算机世界”的抽象过程。本项目完全符合这一设计路径：

- 现实世界：课程项目中的文献、作者、期刊、分类、附件、用户
- 信息世界：实体、属性、联系、约束
- 计算机世界：`users`、`documents`、`authors`、`sources`、`files` 等表，以及外键、唯一约束、索引

例如：

- 现实中的“文献有多个作者，作者可属于多个文献”
- 在信息模型里变成多对多联系
- 在计算机世界里落地为 `DocumentAuthor` 关联表

### 4. 数据管理技术的新发展

课程在概论中会谈到数据库技术的新发展。本项目虽然主体仍是关系数据库，但已经出现了工程化延申：

- ORM 替代纯手写 SQL
- Alembic 迁移替代手工改表
- JSON 文本字段保存半结构化内容，如 `metadata_json`、`summary_json`、`payload_json`
- PDF 识别结果再入库，形成“非结构化输入 -> 结构化存储”的工作流

因此，这一章在项目中不是“停留在概念”，而是已经体现为现代数据库应用开发方式。

## 第2章 关系数据库基本原理

### 1. 关系、元组、属性

项目中的每个模型类本质上都对应一张关系表：

- `User`
- `Category`
- `Document`
- `Author`
- `Affiliation`
- `Keyword`
- `Tag`
- `Source`
- `Publisher`
- `File`
- `AIAgentActivity`
- `AIAgentJournal`
- `MergeAudit`

每个对象实例就是元组，每个字段就是属性。

### 2. 主码、候选码、外码

这一部分在项目中使用得非常完整：

- 主码：几乎每张表都以 `id` 作为主键
- 复合主键：`DocumentAuthor`、`DocumentKeyword`、`DocumentTag`、`AuthorAffiliation`、`AuthorCode`、`UserSetting` 等表都使用了复合主键
- 外键：`Document.user_id -> User.id`、`Document.category_id -> Category.id`、`Document.source_id -> Source.id` 等
- 候选键/唯一性：通过 `unique=True` 和 `UniqueConstraint` 实现

具体例子：

- `User.username` 唯一
- `User.email` 唯一
- `Publisher(user_id, name)` 唯一
- `Source(user_id, name, type)` 唯一
- `Author(user_id, name, code)` 唯一
- `Document(user_id, barcode)` 唯一
- `Document(user_id, copy_no)` 唯一

这说明项目不是只满足“能存数据”，而是已经显式实现了关系模型中的键约束。

### 3. 关系代数思想

项目没有手写“关系代数表达式”，但查询写法本质上在执行关系代数操作：

- 选择：`filter_by(...)`、`filter(...)`
- 投影：接口只返回部分字段，例如自动补全接口只返回名称列表
- 连接：`join(DocumentAuthor, ...)`、`join(Source, ...)`
- 分组：`group_by(Document.id)`
- 排序：`order_by(...)`
- 去重统计：`count(distinct(...))`

因此，课程里的关系代数并不是“没用”，而是通过 ORM 查询 API 被工程化实现了。

### 4. 规范化理论

项目的表结构明显体现了规范化思想：

- 文献、作者、机构、关键词、标签、来源、出版方分别拆表
- 多对多关系通过中间表表达
- 重复出现的名字型实体单独建字典表
- 分类树使用 `categories` 的自引用结构，而不是把多级分类硬编码成多个列

这样做减少了冗余，避免了“一个作者名改动要改几十条文献记录”的问题，这正是规范化的目标。

### 5. 完整性约束

课程里的实体完整性、参照完整性、用户定义完整性，本项目都有对应实现：

- 实体完整性：主键非空且唯一
- 参照完整性：大量 `ForeignKey`
- 用户定义完整性：
  - `Enum` 约束，如 `document_type`、`reading_status`、`approval_status`
  - `nullable=False`
  - 唯一约束
  - 应用层补充校验，例如密码强度、分类归属、用户审批状态

## 第6章 数据查询与管理

这一章是本项目使用最充分的一章。

### 1. 插入数据

项目中的插入并不是直接写 `INSERT INTO ...`，而是通过 ORM：

- `db.session.add(...)`
- `db.session.flush()`
- `db.session.commit()`

典型场景：

- 注册用户插入 `User`
- 新建文献插入 `Document`
- 新作者插入 `Author`
- 新关键词插入 `Keyword`
- 新标签插入 `Tag`
- 新来源插入 `Source`
- 新附件插入 `File`

### 2. 修改数据

项目通过“先查出对象，再改属性，再提交”的方式实现更新：

- 编辑文献
- 修改分类名称
- 审核用户
- 修改 AI 设置
- 修改 MinerU 地址
- 变更文献分类

另外还有批量更新，例如删除分类时：

- `Document.query.filter_by(category_id=cat.id).update({"category_id": None})`

这就是课程中 `UPDATE` 的 ORM 化实现。

### 3. 删除数据

项目中的删除场景也很丰富：

- 删除文献
- 批量删除文献
- 删除分类
- 删除词典项
- 删除附件
- 清理孤立记录

这里不仅有简单删除，还有“先解除关联，再删除主记录”的完整逻辑，体现了对参照完整性的处理。

### 4. 单表查询

典型单表查询包括：

- `User.query.filter_by(username=username).first()`
- `Category.query.filter_by(user_id=current_user.id).order_by(Category.name).all()`
- `Tag.query.filter_by(user_id=uid).order_by(Tag.name).all()`

### 5. 多表查询

多表查询在项目里大量存在：

- 文献搜索时根据作者、标签、来源联查
- 作者自动补全时联查文献表获取示例文献
- 重复合并预览时联查来源和文献
- 多对多关系通过关联表完成连接

### 6. 条件查询、模糊查询、排序、分页、聚合

项目几乎覆盖了这一章的大部分查询知识点：

- 条件查询：`filter_by`、`filter`
- 范围查询：年份上下界

- 排序：`order_by(...)`
- 分页：`paginate(page=..., per_page=...)`
- 聚合：`func.count(...)`
- 去重统计：`func.distinct(...)`

其中标签搜索还做了“命中标签数排序”，已经超出最基础的单表查询。

## 第9章 触发器、权限管理、事务

### 1. 触发器

项目没有使用 MySQL 触发器。

但是它有一个非常重要的“延申实现”：

- 使用 SQLAlchemy 的 `@event.listens_for(..., "before_insert"/"before_update")`
- 在写入前统一规范时间字段

这在效果上类似“应用层触发器”，虽然不是数据库原生 `TRIGGER`，但体现了同样的自动化一致性维护思想。

### 2. 权限管理

项目没有使用 MySQL 的 `GRANT` / `REVOKE` 做数据库账户权限管理。

它采用的是“应用层权限模型”：

- `is_admin`
- `can_review_registrations`
- `is_approved`
- `approval_status`

然后在 Flask 路由中通过装饰器和角色判断控制访问。

所以这一章可以写成：项目实现了权限管理，但实现位置在应用层，而不是 SQL 用户权限层。

### 3. 事务处理

事务是本项目真正大量使用的知识点。

主要表现为：

- 正常提交：`db.session.commit()`
- 异常回滚：`db.session.rollback()`
- 中间刷写：`db.session.flush()`

典型事务场景：

- 新建文献及其作者、关键词、标签、附件
- 批量 BibTeX 导入
- 词典项合并与回滚
- 清理孤立记录
- 审核用户
- AI 日志与周报写入

尤其是 `merge_apply` / `merge_rollback`，已经不是简单事务，而是“带审计记录的可逆事务流程”。

### 4. 锁

课程中事务通常会延伸到锁。本项目在 `allocate_new_author` 中使用了：

- `with_for_update()`

它用于在并发场景下安全地分配同名作者的新编号，避免两个请求同时拿到同一个 `next_code`。这属于非常典型的数据库并发控制知识点，已经超出基础 CRUD。

## 第11章 查询优化

- 高频排序列建索引

- 使用分页而不是一次加载所有文献列表

### 3. 物理查询计划生成

项目代码没有显式 `EXPLAIN`，也没有手动干预优化器，但它通过良好的索引和查询写法，把计划生成的空间交给了数据库优化器。

### 4. 一个典型的优化例子

标签搜索里，项目不是简单地“查出所有文献再在 Python 里筛”，而是：

- 在数据库中 `join` 关联表
- 用 `count(distinct(...))` 计算标签命中数
- `group_by(Document.id)`
- 再按命中数和更新时间排序

这说明项目已经把“尽量让数据库完成筛选和排序”这一优化思想用到了实际代码里。

## 6. 项目中使用到的延申知识点

这部分是本项目相对课程基础内容更“工程化”的地方。

### 1. ORM 映射

项目主要通过 SQLAlchemy ORM 生成 SQL，而不是直接堆叠原生 SQL 语句。这是现代 Web 项目很常见的数据库开发方式。

### 2. Alembic 迁移

课程里通常更关注“表怎么建”，项目则更进一步，考虑了“表将来如何演化”，这就是 Alembic 的价值。

### 3. 旧库兼容修复

`schema_bootstrap.py` 通过原生 SQL 自动补列、补默认值、修旧数据，这是典型的生产级维护思路。

### 4. 应用层触发器思想

SQLAlchemy 事件钩子在插入/更新前统一规范时间字段，这相当于把“触发器思想”放到了 ORM 层。

### 5. 行锁与并发控制

`with_for_update()` 用于作者编号分配，体现了并发写入控制，属于数据库工程中很实用但课堂初学阶段不一定真正落地的内容。

### 6. 审计与可回滚合并

`MergeAudit` 把词典合并前后的变化写成审计记录，并支持回滚。这是“事务 + 审计 + 可恢复”的组合设计。

### 7. 半结构化数据入关系库

AI 活动元数据、合并摘要和负载以 JSON 文本存储在表中，体现了关系库和半结构化数据结合的思路。

### 8. 应用层权限体系

项目没有直接用数据库账户权限，而是把权限控制抽象成业务字段和路由守卫，这更符合现代 Web 应用的真实架构。

## 7. 最后总结

如果从课程角度评价，这个项目对数据库知识的使用重点非常明确：

- 用得最充分的是：关系模型设计、约束、CRUD、多表查询、索引、事务、查询优化意识
- 用得较少但有延申的是：权限管理、触发器思想、半结构化数据管理
- 暂未使用的是：视图、存储过程、数据库原生触发器、分布式数据库、NoSQL 独立方案

因此，这个项目可以被准确概括为：

> 一个以 MySQL 关系数据库为核心、以 SQLAlchemy ORM 为主要 SQL 实现方式、已经具备规范化建模、复杂查询、事务控制、迁移维护和一定工程化扩展能力的课程级文献管理系统。

如果后续要继续写成课程报告，可以把全文进一步浓缩成三个结论：

1. 这个项目确实使用了 SQL，而且使用得很系统，只是主要通过 ORM 间接生成。
2. 课程中的核心知识点，尤其是关系模型、约束、CRUD、索引、事务，在项目中都有真实落地。
3. 项目还延申使用了 ORM、迁移、应用层触发器、行锁、审计回滚等更偏工程实践的知识点。
